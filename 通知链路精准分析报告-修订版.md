## 1. 核心架构与职责边界总览

### 1.1 四层职责边界模型

```
┌─────────────────────────────────────────────────────────────────────┐

│  - 输出: notification_urls/title/body/format 的最终值                 │

                              ↓ (决策结果)

                              ↓ (参数字典)

│                                                                       │
```

## 2. 变量级联决策层详细分析

### 2.1 级联决策核心算法

**函数位置**: `changedetectionio/notification_service.py:17-54`

```python
def _check_cascading_vars(datastore, var_name, watch):
    """
    三级优先级级联决策算法
    
    优先级: 监控级配置 → 标签级配置 → 全局级配置 → 默认值
    """
    from changedetectionio.notification import (
        USE_SYSTEM_DEFAULT_NOTIFICATION_FORMAT_FOR_WATCH,
        default_notification_body,
        default_notification_title
    )

    # ────────── 第一优先级：监控级配置 ──────────
    v = watch.get(var_name)
    if v and not watch.get('notification_muted'):
        # 特殊处理: 如果监控级选择了"使用系统默认"，则继续向下查找
        if var_name == 'notification_format' and v == USE_SYSTEM_DEFAULT_NOTIFICATION_FORMAT_FOR_WATCH:
            return datastore.data['settings']['application'].get('notification_format') or default_notification_format
        return v

    # ────────── 第二优先级：标签级配置 ──────────
    tags = datastore.get_all_tags_for_watch(uuid=watch.get('uuid'))
    if tags:
        for tag_uuid, tag in tags.items():
            v = tag.get(var_name)
            if v and not tag.get('notification_muted'):
                # 注意: 找到第一个匹配的标签即返回，不再检查其他标签
                return v

    # ────────── 第三优先级：全局级配置 ──────────
    if datastore.data['settings']['application'].get(var_name):
        return datastore.data['settings']['application'].get(var_name)

    # ────────── 第四优先级：硬编码默认值 ──────────
    if var_name == 'notification_format':
        return USE_SYSTEM_DEFAULT_NOTIFICATION_FORMAT_FOR_WATCH
    if var_name == 'notification_body':
        return default_notification_body
    if var_name == 'notification_title':
        return default_notification_title

    return None
```

### 2.2 级联决策的调用时机与边界

**调用位置**: `changedetectionio/notification_service.py: send_content_changed_notification()`

```python
def send_content_changed_notification(self, watch_uuid):
    """
    级联决策执行点 - 【在队列入队前执行】
    
    边界特征:
    1. 在构建 NotificationContextData 时同步执行
    2. 结果直接存入 n_object，成为后续所有处理的输入源
    3. 只执行一次，不随渠道变化而变化
    """
    n_object = NotificationContextData()
    watch = self.datastore.data['watching'].get(watch_uuid)
    
    # ────────── 级联决策边界开始 ──────────
    # 为每个通知变量独立执行三级优先级查找
    n_object['notification_urls'] = _check_cascading_vars(self.datastore, 'notification_urls', watch)
    n_object['notification_title'] = _check_cascading_vars(self.datastore, 'notification_title', watch)
    n_object['notification_body'] = _check_cascading_vars(self.datastore, 'notification_body', watch)
    n_object['notification_format'] = _check_cascading_vars(self.datastore, 'notification_format', watch)
    # ────────── 级联决策边界结束 ──────────
    
    # 结果已固化到 n_object，后续流程不再做配置级决策
    
    # 附加 LLM 结果（不参与级联决策，直接透传）
    n_object['_llm_result'] = watch.get('_llm_result')
    n_object['_llm_intent'] = watch.get('_llm_intent', '')
    n_object['_llm_change_summary'] = watch.get('_llm_change_summary', '')
    
    # 入队（决策结果随 n_object 进入队列）
    count = watch.get('notification_alert_count', 0) + 1
    self.datastore.update_watch(uuid=watch_uuid, update_obj={'notification_alert_count': count})
    self.queue_notification_for_watch(n_object=n_object, watch=watch)
```

### 2.3 级联决策的输入输出

| 输入变量 | 查找层级 | 输出 | 说明 |
|---------|---------|------|------|
| `notification_urls` | 4 级 | `list[str]` | 通知目标 URL 列表 |
| `notification_title` | 4 级 | `str` | 通知标题模板 |
| `notification_body` | 4 级 | `str` | 通知正文模板 |
| `notification_format` | 4 级 | `str` | 输出格式: `html`/`htmlcolor`/`markdown`/`text` |

**决策特性**:
- **一次决策，全链路复用**: 决策结果随 `n_object` 贯穿整个通知生命周期
- **变量独立决策**: 每个变量独立走完整的级联查找链，4 个变量可能来自不同层级
- **静音状态检查**: 每一级查找都检查对应的 `notification_muted` 标志

### 3.1 参数组装的两个阶段

参数组装分为 **前置通用组装** 和 **按需差异渲染** 两个阶段：

```
┌─────────────────────────────────────────────────────────────────┐
│          阶段 A: 前置通用组装 (create_notification_parameters)      │
│  调用时机: process_notification() 最开始，循环处理渠道之前            │
│  执行次数: 只执行 1 次，结果被所有渠道共享                            │
└─────────────────────────────────────────────────────────────────┘

```

### 3.2 阶段 A：前置通用组装

**函数位置**: `changedetectionio/notification/handler.py:501-552`

```python
def create_notification_parameters(n_object: NotificationContextData, datastore):
    """
    参数组装核心函数 - 【渠道循环前执行，只执行 1 次】
    
    组装内容分类:
    1. 系统基础 URL 配置
    2. 监控元数据注入
    3. 页面链接生成
    4. 额外 Token 扩展
    """
    
    # ────────── 1. 系统基础 URL 配置 ──────────
    ext_base_url = datastore.data['settings']['application'].get('active_base_url').strip('/')+'/'

    # ────────── 2. 监控元数据注入 ──────────
    watch = datastore.data['watching'].get(n_object['uuid'])
    if watch:
        watch_title = datastore.data['watching'][n_object['uuid']].label
        tag_list = []
        tags = datastore.get_all_tags_for_watch(n_object['uuid'])
        if tags:
            for tag_uuid, tag in tags.items():
                tag_list.append(tag.get('title'))
        watch_tag = ', '.join(tag_list)
    else:
        watch_title = 'Change Detection'
        watch_tag = ''

    watch_url = n_object['watch_url']

    # ────────── 3. 页面链接生成 ──────────
    uuid = n_object['uuid']
    if n_object.get('timestamp_from') and n_object.get('timestamp_to'):
        # 带版本号的差异对比链接
        diff_url = f"{ext_base_url}diff/{uuid}?from_version={n_object['timestamp_from']}&to_version={n_object['timestamp_to']}"
    else:
        # 通用差异对比链接
        diff_url = f"{ext_base_url}diff/{uuid}"

    preview_url = f"{ext_base_url}preview/{uuid}"
    edit_url = f"{ext_base_url}edit/{uuid}"

    # ────────── 4. 统一写入 n_object ──────────
    n_object.update({
        'base_url': ext_base_url,
        'diff_url': diff_url,
        'preview_url': preview_url,
        'edit_url': edit_url,
        'watch_tag': watch_tag if watch_tag is not None else '',
        'watch_title': watch_title if watch_title is not None else '',
        'watch_url': watch_url,
        'watch_uuid': n_object['uuid'],
    })

    # ────────── 5. 额外 Token 扩展（插件机制） ──────────
    if watch:
        # 调用 Watch 模型的扩展方法，支持插件注入自定义 Token
        n_object.update(datastore.data['watching'].get(n_object['uuid']).extra_notification_token_values())

    return n_object
```

### 3.3 阶段 B：按需差异渲染

**函数位置**: `changedetectionio/notification_service.py:239-299`

```python
def add_rendered_diff_to_notification_vars(notification_scan_text: str,
                                            prev_snapshot: str,
                                            current_snapshot: str,
                                            word_diff: bool):
    """
    按需差异渲染 - 【性能优化核心机制】
    
    关键设计:
    1. 先扫描模板用到了哪些 {{ diff_* }} Token
    2. 只渲染实际用到的差异变体，避免不必要的性能开销
    3. 8 种 diff 变体 + 2 种 extract 变体按需创建
    """
    import re

    # 定义 8 种 diff 变体的基础配置
    diff_specs = {
        'diff': {'word_diff': word_diff},
        'diff_clean': {'word_diff': word_diff, 'include_change_type_prefix': False},
        'diff_added': {'word_diff': word_diff, 'include_removed': False},
        'diff_added_clean': {'word_diff': word_diff, 'include_removed': False, 'include_change_type_prefix': False},
        'diff_full': {'word_diff': word_diff, 'include_equal': True},
        'diff_full_clean': {'word_diff': word_diff, 'include_equal': True, 'include_change_type_prefix': False},
        'diff_patch': {'word_diff': word_diff, 'patch_format': True},
        'diff_removed': {'word_diff': word_diff, 'include_added': False},
        'diff_removed_clean': {'word_diff': word_diff, 'include_added': False, 'include_change_type_prefix': False},
    }

    from changedetectionio.diff import extract_changed_from, extract_changed_to
    extract_specs = {
        'diff_changed_from': extract_changed_from,
        'diff_changed_to': extract_changed_to,
    }

    ret = {}
    rendered_count = 0
    
    # ────────── 核心逻辑：先扫描，后渲染 ──────────
    for key in NotificationContextData().keys():
        if not key.startswith('diff'):
            continue
        
        # 用正则扫描模板中是否存在该 Token
        pattern = rf"(?<![A-Za-z0-9_]){re.escape(key)}(?![A-Za-z0-9_])"
        if not re.search(pattern, notification_scan_text, re.IGNORECASE):
            continue  # 没用到，跳过，节省性能
        
        # 模板用到了，才实际渲染这个差异变体
        if key in diff_specs:
            ret[key] = FormattableDiff(prev_snapshot, current_snapshot, **diff_specs[key])
            rendered_count += 1
        elif key in extract_specs:
            ret[key] = FormattableExtract(prev_snapshot, current_snapshot, extract_fn=extract_specs[key])
            rendered_count += 1

    if rendered_count:
        logger.trace(f"Rendered {rendered_count} diff placeholder(s) {sorted(ret.keys())}")

    return ret
```

### 3.4 级联决策 vs 参数组装 - 职责边界对比

| 维度 | 变量级联决策 | 参数组装 |
|------|-------------|---------|
| **核心问题** | 该用哪个配置？ | 用哪些数据渲染？ |
| **执行时机** | 入队前 (send_content_changed_notification) | 出队后，渠道循环前 (process_notification) |
| **执行次数** | 1 次 | 1 次 |
| **输入** | datastore + watch 对象 | n_object + datastore |
| **输出** | 4 个配置变量的最终值 | 20+ 个 Token 组成的完整参数字典 |
| **决策逻辑** | 三级优先级查找 | 数据注入 + 按需计算 |
| **可变性** | 结果一旦确定，全程不变 | 结果可被后续安全处理修改 |
| **性能开销** | 极小（内存查找） | 中等（差异渲染可能耗时） |
| **扩展性** | 固定 4 级层级 | 支持 extra_notification_token_values 扩展 |

## 4. 渠道下发阶段：先逐条登记后统一触发的执行边界

### 4.1 代码结构全景

```python
with (apprise.LogCapture(level=apprise.logging.DEBUG) as logs):
    # ════════════════════════════════════════════════════════════
    # 第一阶段：逐条登记阶段 (循环内)

        # ────────── 子步骤 2: 逐渠道格式适配 ──────────
        if 'html' in requested_output_format:

        # 每个渠道可能得到不同的 n_body/n_title

            n_body=n_body,
            n_title=n_title,
            requested_output_format=requested_output_format_original
        )

        # ────────── 子步骤 3: 确定 Apprise 输入格式 ──────────
        apprise_input_format = "NO-THANKS-WE-WILL-MANAGE-ALL-OF-THIS"
        if not 'format=' in url:

            prefix_add_to_url = '?' if not parsed_url.query else '&'
            
            if 'html' in requested_output_format:
                url = f"{url}{prefix_add_to_url}format={NotifyFormat.HTML.value}"
                apprise_input_format = NotifyFormat.HTML.value
            elif 'text' in requested_output_format:
                url = f"{url}{prefix_add_to_url}format={NotifyFormat.TEXT.value}"
                apprise_input_format = NotifyFormat.TEXT.value
            elif requested_output_format == NotifyFormat.MARKDOWN.value:
                from apprise.conversion import markdown_to_html
                n_body = n_body.replace('---', '\n\n---\n\n')
                n_body = markdown_to_html(n_body)
                url = f"{url}{prefix_add_to_url}format={NotifyFormat.HTML.value}"
                requested_output_format = NotifyFormat.HTML.value
                apprise_input_format = NotifyFormat.HTML.value
        else:
            # URL 中自带了 format= 参数，用户自行负责
            if 'format=html' in url:
                n_body = newline_re.sub('<br>\r\n', n_body)
                apprise_input_format = NotifyFormat.HTML.value
                requested_output_format = NotifyFormat.HTML.value
            elif 'format=text' in url:
                apprise_input_format = NotifyFormat.TEXT.value
                requested_output_format = NotifyFormat.TEXT.value

        # ────────── 子步骤 4: 记录发送对象（调试用） ──────────
        sent_objs.append({
            'title': n_title,
            'body': n_body,
            'url': url,
            'original_context': n_object
        })

        # ────────── 子步骤 5: 逐条登记到 Apprise ──────────
        # 【边界点】apobj.add(url) - 只登记，不发送
        if not url.startswith('null://'):
            apobj.add(url)  # ⚠️  只是"注册"目标，不触发发送

        # ────────── 子步骤 6: 邮件特殊美化（在循环内！） ──────────
        # 注意：这行代码在 for 循环内部，但修改的是循环变量 n_body
        # 问题：这个修改只对最后一个 mail URL 有效吗？
        if url.startswith('mail') and 'html' in requested_output_format:
            if not '<pre' in n_body and not '<body' in n_body:
                n_body = as_monospaced_html_email(content=n_body, title=n_title)

    # ════════════════════════════════════════════════════════════
    # 第二阶段：统一触发阶段 (循环外)
    # 边界: for 循环结束后的代码
    # ════════════════════════════════════════════════════════════
    
    # 【关键 Bug 点】apobj.notify() 在循环外面！
    # 使用的是最后一次循环的 n_title, n_body, apprise_input_format
    if not url.startswith('null://'):  # ⚠️  这里用的 url 是循环最后一次的值！
        apobj.notify(
            title=n_title,          # ⚠️  最后一次循环的值！
            body=n_body,            # ⚠️  最后一次循环的值！
            body_format=apprise_input_format,  # ⚠️  最后一次循环的值！
            attach=n_object.get('screenshot', None)
        )

    # 返回所有渠道的发送记录
    return sent_objs
```

```
    │  URL 1 渲染处理  │         │  URL 2 渲染处理  │         │  URL N 渲染处理  │
    │  ─────────────── │         │  ─────────────── │         │  ─────────────── │
    │  jinja_render()  │         │  jinja_render()  │         │  jinja_render()  │
    │  apply_service_tweaks()    │  apply_service_tweaks()    │  apply_service_tweaks() │
    │  apobj.add(URL_1) │         │  apobj.add(URL_2) │         │  apobj.add(URL_N) │
    └────────┬────────┘         └────────┬────────┘         └────────┬────────┘
             │                            │                            │
             └────────────────────────────┼────────────────────────────┘
                                          │
                                ┌─────────▼─────────┐
                                │  Apprise 内部状态  │
                                │  ┌───────────────┐│
                                │  │ URL 1 (已登记)││
                                │  │ URL 2 (已登记)││
                                │  │ URL N (已登记)││
                                │  └───────────────┘│
                                └─────────┬─────────┘
                                          │
                                ┌─────────▼─────────┐
                                │  apobj.notify()    │
                                │  【统一触发！】     │
                                │  使用最后一次循环的  │
                                │  n_title / n_body  │
                                │  / apprise_input_format │
                                └───────────────────┘
```

### 4.3 登记阶段与触发阶段的边界特征

| 阶段 | 执行范围 | 关键操作 | 变量作用域 |
|------|---------|---------|-----------|
| **逐条登记阶段** | `for url in n_object['notification_urls']:` 循环内部 | - jinja_render(title/body/url)<br>- apply_service_tweaks()<br>- apobj.add(url) | `n_body`, `n_title`, `apprise_input_format`, `url` 都是**循环局部变量**，每次迭代覆盖 |
| **统一触发阶段** | 循环结束后的代码 | - apobj.notify() | 使用**最后一次循环**的 `n_body`, `n_title`, `apprise_input_format`, `url` 值 |

### 4.4 Apprise 工作机制原理

```
Apprise 实例 = 临时通知缓冲区

1. apobj = apprise.Apprise()        → 创建空的通知缓冲区
2. apobj.add("mailto://...")        → 把邮箱地址加入缓冲区
   apobj.add("slack://...")         → 把 Slack Webhook 加入缓冲区
   apobj.add("discord://...")       → 把 Discord Webhook 加入缓冲区
   ...                              → 所有目标都只是"登记"，不发送
   
3. apobj.notify(title, body, ...)   → 【一次性触发】
                                      给所有已登记的目标发送相同的内容!
```

**关键特性**:
- `add()` 只是注册目标，不执行网络 IO
- `notify()` 执行实际发送，给所有已注册目标发送**相同内容**
- 调用 `notify()` 后，已注册目标不会自动清除，可以继续 add 后再次 notify

## 5. 关键 Bug 分析与影响评估

### 5.1 Bug 确认：多渠道格式污染

**Bug 位置**: `changedetectionio/notification/handler.py:477-486`

**问题代码**:
```python
# 循环处理每个 URL（可能每个 URL 需要不同的格式）
for url in n_object['notification_urls']:
    (url, n_body, n_title) = apply_service_tweaks(...)  # 每个渠道独立格式化
    apobj.add(url)

# 循环结束后，只调用一次 notify
apobj.notify(
    title=n_title,          # ⚠️ Bug：使用最后一次循环的值
    body=n_body,            # ⚠️ Bug：使用最后一次循环的值
    body_format=apprise_input_format,  # ⚠️ Bug：使用最后一次循环的值
    attach=n_object.get('screenshot', None)
)
```

### 5.2 Bug 场景演示

**场景**: 同时配置了 Telegram + Discord 两个通知渠道

| 步骤 | 变量状态 | 说明 |
|------|---------|------|
| **循环 1 (Telegram)** | | |
| | `url = "tgram://..."` | Telegram URL |
| | 调用 `apply_service_tweaks()` → | `<s>` 标记删除，`<b>` 标记新增 |
| | `n_body = "Telegram 格式内容"` | 纯文本 + Telegram 专属 HTML |
| | `apobj.add(tgram_url)` | 登记 Telegram 目标 |
| **循环 2 (Discord)** | | |
| | `url = "discord://..."` | Discord URL |
| | 调用 `apply_service_tweaks()` → | `~~` 标记删除，`**` 标记新增 |
| | `n_body = "Discord 格式内容"` | Markdown 语法 |
| | `apobj.add(discord_url)` | 登记 Discord 目标 |
| **循环结束，调用 notify()** | | |
| | 使用 `n_body = "Discord 格式内容"` | ⚠️  是 Discord 格式！ |
| | 发送给所有已登记目标 | Telegram 收到 Discord 格式！ |

**结果**:
- ✅ Telegram 确实收到了通知
- ❌ Telegram 收到的消息里包含 `~~` 和 `**` Markdown 符号（应该是 `<s>` 和 `<b>`）
- ✅ Discord 收到了通知，格式正确
- ❌ 所有渠道都收到**最后一个渠道**的格式版本

### 5.3 Bug 影响范围评估

| 影响维度 | 严重程度 | 说明 |
|---------|---------|------|
| **单渠道用户** | 无影响 | 只有一个通知 URL 时，完全正常 |
| **多渠道同格式** | 轻微 | 都是纯文本或都是 HTML 时，基本正常 |
| **多渠道混合格式** | 严重 | Telegram + Discord + Email 混合配置时格式混乱 |
| **邮件 HTML 美化** | 不确定 | 邮件美化在循环内，但只对最后一个 mail URL 生效 |
| **URL 内 Token 渲染** | 正常 | URL 本身的 Token 渲染在循环内，每个 URL 独立正确 |

### 5.4 为什么会有这个 Bug？

**设计意图 vs 实际行为偏差**:

```
预期设计（每个渠道独立发送）：        实际实现（统一发送）：

for url in urls:                    for url in urls:
    render body/title                   render body/title
    apply tweaks                        apply tweaks
    apobj.add(url)                      apobj.add(url)
    apobj.notify(title, body)        apobj.notify(title, body)  ← 移到循环外了
                                      只调用一次！
```

**可能的历史原因**:
1. 早期版本只支持单渠道，`notify()` 在循环内外都一样
2. 后来增加多渠道支持时，忘记把 `notify()` 移到循环内
3. 或者误以为 `add()` 时就会发送，`notify()` 只是确认

### 6.2 四层职责边界总结表

| 层级 | 职责边界 | 关键函数 | 输入 | 输出 |
|------|---------|---------|------|------|
| **1. 变量级联决策** | 确定"用哪个配置" | `_check_cascading_vars()` | datastore + watch | 4 个通知配置变量的最终值 |
| **2. 参数组装** | 确定"用哪些数据渲染" | `create_notification_parameters()`<br>`add_rendered_diff_to_notification_vars()` | n_object + datastore | 20+ Token 组成的完整参数字典 |
| **3. 模板渲染** | 模板字符串替换为实际内容 | `jinja_render()` | 模板字符串 + 参数字典 | 渲染后的 title/body/url |
| **4. 渠道下发** | 按渠道格式适配并发送 | `apply_service_tweaks()`<br>`apobj.add()`<br>`apobj.notify()` | 渲染后的内容 | 实际通知到达用户 |

### 6.3 关键设计决策回顾

| 决策点 | 当前实现 | 设计意图 | 副作用/问题 |
|--------|---------|---------|-------------|
| **级联决策时机** | 入队前执行 1 次 | 减少重复计算，队列中只存结果 | 队列中数据不随后续配置变更而更新 |
| **按需差异渲染** | 先扫描模板，后只渲染用到的 diff | 性能优化，避免 8 种无用计算 | 增加了代码复杂度 |
| **参数字典共享** | 所有渠道共享同一份 notification_parameters | 减少内存占用，提升性能 | 无法按渠道定制参数 |
| **逐渠道渲染** | 循环内独立渲染每个渠道的 title/body/url | 支持 URL 中使用 Token（如 `{{watch_uuid}}`） | 增加了循环次数，重复渲染相同内容 |
| **统一触发发送** | `notify()` 在循环外，只调用 1 次 | 减少网络 IO 次数？（Apprise 内部还是逐个发） | ⚠️  多渠道格式污染 Bug |

## 7. 修复建议（针对统一触发 Bug）

### 7.1 方案 A：把 notify() 移到循环内

```python
# 修改前（Bug 版本）
for url in n_object['notification_urls']:
    ... render + tweaks + apobj.add(url)
apobj.notify(title, body, ...)  # 循环外

# 修改后（修复版本）
for url in n_object['notification_urls']:
    ... render + tweaks
    apobj.add(url)
    apobj.notify(title, body, ...)  # 循环内，每个渠道独立发送
    apobj.clear()  # 避免重复发送
```

**影响**:
- ✅ 每个渠道收到自己格式版本的内容
- ⚠️  网络 IO 次数从 1 次变成 N 次（但 Apprise 内部本来就是逐个发）
- ⚠️  日志数量增加

### 7.2 方案 B：每个渠道独立 Apprise 实例

```python
for url in n_object['notification_urls']:
    ... render + tweaks
    per_channel_apobj = apprise.Apprise()  # 每个渠道独立实例
    per_channel_apobj.add(url)
    per_channel_apobj.notify(title, body, ...)
```

**影响**:
- ✅ 完全隔离，互不干扰
- ⚠️  内存占用略增（但可忽略）

### 7.3 方案 C：分组发送（按格式类型）

```python
# 按输出格式分组 URL
format_groups = {}
for url in n_object['notification_urls']:
    ... render + tweaks
    # 根据 format 分组
    fmt = apprise_input_format
    if fmt not in format_groups:
        format_groups[fmt] = {'urls': [], 'title': title, 'body': body}
    format_groups[fmt]['urls'].append(url)

# 按组发送
for fmt, group in format_groups.items():
    apobj = apprise.Apprise()
    for url in group['urls']:
        apobj.add(url)
    apobj.notify(group['title'], group['body'], body_format=fmt)
```

**影响**:
- ✅ 相同格式的渠道批量发送，减少重复
- ⚠️  实现复杂度增加
